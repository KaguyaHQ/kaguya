# Merging visual novel records

Use this procedure when multiple Kaguya records represent the same work, or when
moderators deliberately combine separate parts of one work. The operator decides
which records belong together. The merge engine does not discover duplicates.

Implementation: [`Kaguya.VisualNovels.Merge`](../lib/kaguya/visual_novels/merge.ex).
CLI: [`mix kaguya.merge_vns`](../lib/mix/tasks/kaguya.merge_vns.ex).
Behavior tests: [`merge_test.exs`](../test/kaguya/visual_novels/merge_test.exs).

## 1. Establish the identity and choose the survivor

Confirm the same work using descriptions, original/translated titles, developers,
release dates, and store IDs. A shared title alone is insufficient: different
games can have the same name. Record the evidence and classify the operation as
either **duplicate copies** or **combining separate parts**.

Record each live production UUID, slug, and VNDB ID. UUIDs generated by an import
into a local rehearsal database differ from those generated in production;
resolve production records again before execution.

Choose one **canonical** record to survive and list the other records as
**sources**. Prefer the established record when it has member edit history and
an existing public URL. When an older VNDB-linked catalog record already exists,
it can remain canonical. Record the choice explicitly for each group.

The engine keeps the canonical's VNDB ID by default. Keeping an unlinked member
record requires a reviewed context script: in an outer transaction, clear the
duplicate's VNDB ID, then merge with that ID explicitly assigned to the survivor.
This avoids a unique-key conflict and prevents the live ID from being registered
as merged away. Both steps must commit or roll back together. Do not clear the
ID as a separate operation, or merge the VNDB-linked source first and assign its
ID afterward. The plain CLI does not perform this identity transfer.

Source VNDB IDs are recorded in `vn_merges` and excluded from future imports.
Do not register the surviving VNDB ID as a merged-away ID. If another survivor
is needed, review ID assignment and the sync skip-list explicitly.

A source cannot itself be the canonical of a previous merge. Resolve that case
before proceeding; the engine rejects merge chains rather than flattening them.

## 2. Record the field and user-data decisions

Review the proposed metadata instead of accepting every default. Current defaults:

| Field | Resolution |
| --- | --- |
| Title, slug, original language, VNDB ID | Keep canonical values |
| Description | Longest nonblank description |
| Aliases | Union, including source titles |
| Release date | Earliest date |
| Reading length | Sum minutes and derive a length category |
| VNDB vote count/rating | Sum counts; compute vote-weighted rating |
| Cover and featured screenshot | First non-null, canonical first |
| Cover fallback URL (`temp_image_url`) | First non-null, canonical first |
| Content/moderation flags | Flags can carry across from any record |
| Title category | `nukige` takes precedence over `adjacent`, then `vn` |
| Primary series fields | Cleared; inspect resulting series membership |

For **duplicate copies**, choose one supported reading length and its matching
category; adding durations would count the same game repeatedly. Likewise, do
not add the same VNDB votes twice if duplicate records contain copied statistics.
Review descriptions, language, category, covers, locks, visibility, and age flags
against the member's edits. Longest text or the broadest flag is not necessarily
the desired editorial result.

Source revision histories are not reparented into the canonical history. The
engine writes a new system merge revision on the canonical. Because dump-sync
protection checks for user revisions on the surviving UUID, merging a member
entry does not automatically give the survivor that member entry's protection.
Before another import, verify that curated content on the survivor is protected
through the normal user/moderator revision workflow. Record this in the merge
plan; changing the canonical's metadata alone does not establish protection.

Per-user conflicts are resolved as follows. A row that has no competing row for
the same user is moved to the canonical. Competing rows are reduced to a winner:

| Data | Current conflict rule |
| --- | --- |
| Ratings | Latest `updated_at`, then UUID |
| Reviews | Latest `updated_at`, then longest content, then UUID |
| Reading status | `read` > `currently_reading` > `on_hold` > `did_not_finish` > `not_interested` > `want_to_read`; ties use latest update, then UUID |
| Shelf membership | One membership per shelf |
| List membership | One placement per list |
| Personal tag votes | Latest `inserted_at` per user/tag, then UUID |
| Similarity votes | Composite-key conflict handling, described below |

Generic composite-key conflicts keep the canonical's row when present. Otherwise
the implementation picks a source row by PostgreSQL `ctid`. This also applies to
list placement, same-language titles, same-site external links, and several
catalog associations. It does **not** guarantee the lowest list position or
latest similarity vote, and the source winner can differ after a database restore.
Record an explicit decision for meaningful conflicts before executing a merge.
Rows with a null conflict key are kept distinct, matching PostgreSQL unique
index behavior. In particular, unrelated manual covers without VNDB image IDs
must all survive; a missing ID is not evidence that the images are duplicates.

Count and inspect ratings, reviews, reading statuses, shelves/lists, votes,
images, releases, relations, series, and references such as favorites. Save the
expected surviving user rows, including the winning values when one user used
multiple copies. Raw row counts may decrease legitimately after deduplication.

## 3. Preview and rehearse

Read `mix help kaguya.merge_vns`. In an environment configured for the intended
database, omitting `--execute` previews the merge:

```bash
mix kaguya.merge_vns \
  --canonical=surviving-vn \
  --sources=duplicate-one,duplicate-two
```

The preview validates identities and computes resolved metadata. It does not
execute or roll back the migration SQL, enumerate all user-data conflicts, or
prove that constraints and post-merge search cleanup will succeed. Save the full
`resolved_attrs` from the context when reviewing fields omitted by CLI output.

The CLI supports title/slug overrides only. Other reviewed overrides require the
context API in an operation-specific script, using trusted UUIDs and values:

```elixir
Merge.merge_vns(canonical_id, source_ids, actor_user_id,
  dry_run: true,
  attrs: %{length_minutes: reviewed_minutes, length_category: reviewed_category}
)
```

Set both length fields because overrides are applied after automatic category
derivation. Use the identical IDs and override map for execution, changing only
`dry_run` to false. Do not pass unreviewed external maps as overrides.

Perform a real merge on a restored local copy and check the outcomes listed
below. Run focused merge tests when changing merge code. Use a separate clone
for the rehearsal; do not reset a developer's existing database.

Do not rename the canonical to a slug still occupied by a source in the same
merge: the canonical update happens before source deletion. Plan any preferred
URL change separately and retain redirects.

## 4. Execute the reviewed production plan

Before writing, obtain approval for the concrete survivors, sources, overrides,
and conflict outcomes. Take a fresh backup, record its location and checksum,
and confirm the restore procedure. The merge registry is an audit trail, not an
undo mechanism.

For this procedure, pause web writes and other writers affecting these records
while taking the final baseline and merging. The engine takes a canonical
advisory lock; that is not a substitute for preventing concurrent source edits.
Keep PostgreSQL and Meilisearch available. Arrange recovery of site availability
if the job fails.

A source checkout with Mix can execute a reviewed CLI plan with `--execute`.
A deployed release may not include Mix; use a reviewed release-operation script
calling the same context, with the web endpoint and background jobs disabled.
Check the target database and installed application version explicitly.

Use an actual moderator `actor_user_id` with the context when operator attribution
is required. The CLI currently passes `nil`: it writes a system revision and
merge registry entries but no actor-attributed `audit_log` entry. Retain the
operator and execution output in the run record.

The database work runs in one transaction per merge group: dependent rows move,
the canonical is updated, redirects and merge history are recorded, source rows
are deleted, and rating aggregates/tag relevance are recomputed. A batch of
separate groups is not one transaction. Stop on the first failure and determine
which groups committed before retrying.

## 5. Verify and restore availability

For every group, verify:

- The canonical exists with the reviewed metadata and VNDB ID. Source rows are
  absent, with the expected registry entries and system revision present.
- All expected user rows and winning conflict values survived, including reviews,
  statuses, list/shelf placement, votes, favorites, and activity references.
- Covers/screenshots still load. Releases, relations and series membership point
  to the expected records; source aliases remain searchable.
- Every old URL resolves to the canonical, including any canonical URL changed
  by a separately reviewed rename. The current LiveView can serve the surviving
  record at the old URL with HTTP 200 and a canonical link; verify the rendered
  record and canonical metadata rather than assuming an HTTP 301 redirect.
- Meilisearch contains the canonical, removed source documents are absent, and
  all submitted search tasks succeeded. Check both English and alternate titles.
  Search ranking alone cannot establish how many database records remain.
- Browse/detail caches and the public page show the resulting record correctly.

Search updates and browse-cache refresh happen after the database commits. The
engine logs cleanup exceptions as non-fatal, and a successful return does not
prove search tasks succeeded. Repair failed indexing/cache refresh without
repeating an already committed merge. Do not repeat the merge to remove a stale
search result.

Restore normal routing and writers after verification. If a database transaction
fails, confirm rollback and record the error. If a committed merge needs reversing,
use the backup and recorded baseline to plan a targeted recovery; do not assume
rerunning an older full backup on a live database will preserve later activity.

Retain the identity evidence, approved plan, exact overrides, baseline, backup
checksum, application version, execution results, and verification results.
